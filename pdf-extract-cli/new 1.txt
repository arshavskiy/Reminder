CLI Tool: Local PDF Data Extraction (Ollama-powered)

Context

The existing web app (server/src/pipeline/) extracts structured data from Hebrew business PDFs (contracts, invoices, inspection reports) using: pdf-parse for text-based PDFs, Tesseract.js OCR as fallback for scans, then an LLM call (OpenAI gpt-4o-mini) to turn raw text into a structured JSON record (client info, dates, contract numbers, etc.).

Goal: a standalone CLI tool, in a new top-level folder, that does the same PDF → structured JSON extraction, but:
- Runs fully locally — no OpenAI dependency, no API costs, works offline.
- Uses Ollama for the text→JSON step instead of OpenAI.
- Is decoupled from the server (per user's choice) — its own code, not importing server/src, so it can be run/shared independently and iterated on quickly without touching the production web app.

This is also a testbed to validate whether small local models are "good enough" for this extraction task before ever considering switching the main app's default backend (out of scope for this task).

Hardware constraint: NVIDIA RTX A2000 Laptop GPU, 4GB VRAM. Research (via Ollama's library + 2025-2026 benchmarks) confirms:
- Local vision-language models have no reliable Hebrew OCR support and are prone to hallucinating text — not safe for this use case. Tesseract.js OCR stays as the OCR engine, ported into the CLI (same engine, standalone copy).
- For text→JSON extraction, best options at 4GB VRAM: qwen3:4b (~2.5GB, best multilingual/instruction-following balance), phi-4-mini (~2.5GB, strong structured-output reliability), qwen3:1.7b (~1.4GB, fastest/most headroom). Avoid anything ≥7B — no VRAM headroom left for context.
- Ollama's format parameter with a JSON Schema (not just "json" mode) gives real grammar-constrained decoding since Ollama 0.3+ — this should be used instead of prompt-only JSON mode, to keep small-model output schema-valid.

Interactive Terminal UI for pdf-extract-cli

(Plan reviewed and confirmed current as of this session — no changes needed to scope below.)

Context

pdf-extract-cli/ (built in a prior session) is a flag-driven CLI:
node src/cli.ts <file|dir> [--model][--out][--no-ai][--verbose]. It runs
Tesseract OCR + a local Ollama model (qwen3:4b recommended after
benchmarking) to turn Hebrew business PDFs into structured JSON, matching the
ExtractionResult shape used by the main app.

The user wants this to feel like a "proper" tool: instead of memorizing
flags, running it with no arguments should launch an interactive terminal
UI — prompts for file path (with autocomplete), model choice, confirmation
— show a live progress indicator while OCR/extraction runs, then a
human-readable results screen (not just raw JSON) with an option to save
JSON + a readable summary to disk.

The existing flag-based invocation must keep working unchanged (for
scripting/batch use, CI, etc.) — the interactive mode is additive, triggered
when no file arguments are given (or via --interactive/no args).

Approach

Use @clack/prompts for the interactive flow — lightweight, zero native
deps (works fine on Windows/PowerShell/Git Bash), good file-path
autocomplete via a custom text prompt + basic FS-based suggestion, spinner
support for the OCR/extraction progress, and styled output for the results
screen. This avoids the much heavier Inquirer or a full TUI framework
(blessed/ink) which would be overkill for a linear wizard flow.

New dependency

- @clack/prompts (~small, pure JS, no native bindings)

Flow (interactive mode)

1. Welcome banner (intro()) — tool name + short description.
2. File/folder path prompt — text() prompt with live validation
(path exists, is .pdf or a directory containing PDFs) using Node's
fs as the user types is not natively supported by clack's text()
(no live autocomplete-as-you-type in a plain text prompt) — implement
lightweight autocomplete by:
  - Accepting a partial path
  - On Tab-less environments (clack doesn't support raw Tab-complete),
instead: after the user types a path, if it doesn't resolve, list
sibling entries in the parent dir that share the typed prefix as
suggestions and let them pick via select(). This is the pragmatic
"autocomplete" approximation without pulling in a raw-keypress-handling
library.
  - If multiple PDFs found (directory input), show a multiselect() to
pick which ones to process (default: all selected).
3. Model selection — select() prompt listing models pulled locally via
ollama list (shell out, parse), with qwen3:4b pre-selected/starred as
recommended (matches README benchmark findings), falling back to a manual
text entry if the Ollama call fails (server not running) or user wants a
model not yet pulled. Include a "skip AI, regex-only" option (maps to
--no-ai).
4. Output preference — select(): "Print to screen only" / "Save to
file(s)" — if saving, text() prompt for output directory (default:
./output), created if missing.
5. Confirmation summary — note() showing chosen file(s), model, output
choice before running.
6. Run — for each file: spinner() start → call existing
runPipeline() (unchanged) → spinner stop with ✓/✗ and one-line status
(used OCR? AI success? timing).
7. Results screen — for each processed file, a formatted human-readable
summary block (not raw JSON): client name/company, document type, key
dates (start/expiry), contact info, confidence — using note() or plain
styled console.log blocks. Full JSON still written to disk if the user
chose to save.
8. Save output (if chosen) — write two files per document into the
output dir:
  - <name>.json — same shape as today (file, used_ocr, regex_fallback,
ai_extraction, etc.)
  - <name>.summary.txt — the human-readable block also shown on screen
9. Outro — outro() with count of files processed, any failures, and
output location if saved.

Table/CSV + HTML extraction with line-count verification

(Approach confirmed with user: per-cell bbox-crop OCR, Python/pdfplumber dependency accepted.)

Context

The universal-PDF-reader rewrite (previous session, now complete and
building clean) turned pdf-extract-cli into a generic "clean text out of
any PDF, optional free-form AI question" tool with no fixed schema.

The user now wants a separate, additive capability: when a PDF contains
a detectable table (tested against a real 19-page Bank Hapoalim statement,
pdf-extract-cli/data/current_account_operations_07.07.2026_11.32.56.pdf),

What was already discovered this session (informs the plan)

- server/src/pipeline/pdfPlumberParser.ts + pdfplumber_extract.py (main
app, already exists) shell out to Python's pdfplumber and return both
raw text AND a structured tables: string[][][][] array ([page][table] [row][cell]) using line-based-then-text-based table-detection strategies.
This is the right tool for structural table detection — reused as-is via
the same subprocess pattern, not reimplemented.
- Tested against the real bank statement: pdfplumber correctly finds one
table per page × 19 pages, with clean columns for date, credit, debit,
balance. BUT this specific PDF embeds a custom subset font
(Poalim-Regular) with a broken/missing Hebrew ToUnicode CMap — the
Hebrew "description" column decodes to � replacement characters at
the character-code level. This is not the bidi-reversal problem
